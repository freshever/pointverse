# Qwen3-VL-2B 本地分类实测

日期：2026-10-22。只读实验，不修改数据库、不调用网络模型。本报告不是正式分类准确率基准。

## 实验条件

- 数据：用户复制的 `test-mode/pointverse-test.sqlite`，148条Point。按App关键词规则与人工覆盖逻辑复现91条未分类；20条旧审阅记录、0条人工分类。
- 模型：`Qwen3-VL-2B-Instruct-Q8_0.gguf`，SHA-256 `b7802e29f71a9e5b5e3f83f613df898a2204342dcea71a231ea501d481813c39`，与App manifest一致。运行时读取架构为qwen3vl，标识规模1.7B。
- 运行时：使用App下载的同一macOS llama.framework，以C++探针调用同样的文本ChatML路径，不加载视觉projector。4096上下文，n_batch/n_ubatch均128，温度0.6，输出最多360 token，固定seed42。App实际采用随机seed，因此结果不保证逐字相同。
- 模型单实例串行测试。首轮大类实际输入约724～811 token，没有超过上下文预算；本次未出现ggml_abort。
- 探针复用模型和上下文，每条清空KV及重建采样器；App会释放并重新加载模型。因此测得的累计推理时间不等于App端到端延迟。

## 实验一：当前大类→细分类流程，91条

读取当前Swift提示词、目录别名和官方英文名称生成同等输入；先全部21大类，成功后在该分支内细分，共110次调用。

| 最终机器状态 | 数量 | 含义 |
|---|---:|---|
| failed | 69 | 首轮分类ID不符合白名单，未进入细分 |
| suggested | 19 | 格式合法，不代表语义正确 |
| uncertain | 3 | 模型主动返回不确定 |

69条首轮失败的原始回复全部是可解析JSON，且全部把名称附在ID里，例如：

`"ids":["lcc:P: 语言与文学 / LANGUAGE AND LITERATURE"]`

这不是JSON解析器无法读取，而是ID不等于合法的 `lcc:P`。只放宽JSON包装不能解决此问题。

19条格式合法的首轮全部选择Z。细分后最终10条Z、9条ZA；其中不少与主题明显不符。其余原始首轮回复中，P出现43次，Q出现8次，G出现10次，其他类别较少。该分布不能视为真实数据主题分布。

问题样本：

- 流星雨：回复将“科学探索”解释成“语言与文学”，ID还附带名称，触发校验失败。
- 番茄幼苗：解释为“语言与文学中关于科学方法的实践性表达”，属于错误归因。
- 京都寺院：以“设计实验”为由选择Z，后续还将安静氛围解释成图书信息整理。
- 堆肥、应急资金：最终选择ZA，格式合法但语义不合理。
- 跑步训练：出现“只是在讨论跑步体验，未涉及具体领域”的不确定理由。

结论：除了格式问题，还有明显的任务理解偏差。把附带名称截掉只能提高机器通过率，不能据此认定分类改善。

## 实验二：只输出大类字母，10条

选取旧流程全部返回uncertain的10条，仍提供21个大类，去掉JSON和理由要求。

- 10条全部输出合法字母，消除了格式失败。
- 但语义错配仍存在：沟通和京都寺院被选为F（美洲地区史），月季养护被选为P，深蹲被选为T。
- 对同10条去除重复的“下一步需要设计一个小实验”尾句后仍全部格式合法，但分类变化很大，流星雨甚至变成F；不是仅清理尾句就能解决。

这是小样本稳定性观察，不作精确准确率比较。

## 实验三：直接输出日常中文主题

不提供LCC字母、不要求JSON，只要求一个日常中文主题；保留原始输入，提示忽略通用实验尾句。

旧10条不确定记录的输出：

|---|---|
| 英仙座流星雨 | 天文 |
| 番茄幼苗生长 | 园艺 |
| 咖啡研磨与萃取 | 咖啡制作 |
| 工业革命 | 工业革命 |

| 面包低温烘焙 | 烘焙 |
| 古代城市发展 | 历史 |

人工查看，这10个主题均与内容相关；不代表完整91条准确率为100%。这些例子的类别并非严格互斥，也没有独立标注的唯一真值。

扩展至全部91条后：

- 91条均有输出，但实验中的theme_output仅表示生成了文本，不等于通过质量校验。
- 2条明显回显原文／混入额外文字；其余大多为短主题，存在颗粒度不一致及误判。
- “丝绸之路”输出旅行，偏浅；“戏剧冲突”输出沟通，丢失创作语境；“用户主动选择网络模型”输出沟通，属于偏题；科幻片段有的输出“城市呼吸”“情感与记忆”，未统一成创作类。
- 该组累计原生推理约15.6秒，对比现流程约194.5秒；输入、输出长度和调用次数不同，不能作为手机端提速倍率承诺。

## 判断与建议

1. 模型文件完整，且能理解这些短文本的大量日常主题；不能简单归结为模型完全不支持分类。
2. 当前让2B模型同时执行LCC符号选择、层级决策、严格JSON和拒绝策略，实际效果差。大类优先虽移除了召回限制，但仍不足以解决该模型的符号分类任务。
3. 优先试验“模型提取日常主题→受控别名归一→映射标准目录”。先让有用的主题标签可见，LCC映射不应成为整理内容的硬门槛。
4. 主题输出仍需长度、回显和重复检查；不可将91条有输出宣传成91条正确归类。正式映射需人工标注评估，尤其区分创作内容与文本中描写的事件。
5. 不建议只放宽ID校验后直接批量入库。本次未自动采用任何结果，数据库仍为20条旧审阅记录、0条人工覆盖。
